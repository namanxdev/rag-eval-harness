# v2 — what changed and why

v1 answered one question: does clause-aware chunking beat fixed-width chunking?
It answered it well, and it could not answer anything else. There was one lever
under test, one metric that generalised, no way to run on anyone else's
documents, and no tests.

v2 turns it into a harness that measures **four levers**, says **why** each
query failed, runs on **a client's own corpus**, and produces a report a
non-engineer can read. Nine commits, each independently useful.

## What was already there

Worth stating plainly, because a plan that rebuilds working code is worse than
no plan. v1 already had: offset-carrying chunkers with two strategies, a Qdrant
dense index, **cross-encoder reranking** (already implemented and already
evaluated), precision/recall/MRR/span-coverage, a deterministic CUAD eval set
builder with checksum verification, and the `doc_id` payload filter.

Reranking was not a v2 feature. Metadata filtering partly existed — as a
scoping mechanism, never evaluated as a lever. v2's job was the gap, not a
rewrite.

## The six changes

### 1. Grounding completeness — `src/metrics.py`

The gap: `span_coverage` pools gold characters across all of a query's spans.
A question needing two clauses scores 0.5 when one comes back whole and the
other is missed entirely, and reads as partial success. It is a wrong answer
with a confident citation.

Added `span_recall@k` (fraction of **distinct** gold spans at least 50%
retrieved) and `complete_grounding@k` (`True` only when every span clears the
bar). Where a query fails, `per_query.json` now carries `missed_spans` — the
offsets and opening text of each clause the answer would have been missing.

The threshold is a fixed constant. Tuning it per run to make a configuration
look better is how these numbers stop meaning anything.

Worked example and the both-directions divergence: [`metrics.md`](metrics.md#why-grounding-exists-a-worked-example).

### 2. Failure taxonomy — `src/taxonomy.py`

Every failing query gets exactly one label, assigned by rule from chunk offsets
and rank positions. **No model call anywhere in it.** That is the selling
point, not a limitation: a client can re-derive any label by hand from two
committed files. A taxonomy a buyer cannot audit is an opinion with a table
around it.

Five labels, first-match-wins, because earlier faults cause later ones. Full
definitions in [`metrics.md`](metrics.md#failure-labels).

Two departures from the original plan, both to stop the taxonomy misattributing
blame:

- **Labels are scoped to the spans that actually failed.** A clause split
  across chunks but retrieved whole did not cause the failure. Unscoped, the
  rule would have swallowed nearly every naive-chunking failure into
  `chunk-severance`.
- **`chunk_stats` could not be reused** as the plan assumed. It returns corpus
  aggregates — `spans_in_one_chunk` as a fraction, `precision_ceiling` as a
  mean — and the labels need per-query, per-span counts that are not
  recoverable from those.

### 3. Corpus adapter — `data/adapt.py`

A delivery blocker: the harness could only run on CUAD. `data/adapt.py` turns a
directory of documents plus a JSONL query file into the same schema
`data/prepare.py` produces. `data/prepare.py` is untouched — CUAD stays the
reference corpus — but its `validate()` is reused, so both paths are held to
one contract rather than two that drift.

It refuses to guess. A `gold_texts` entry matching zero times, or more than
once, raises with the document, the text and the count. Offsets outside the
document raise. A PDF that extracts to nothing raises rather than being indexed
as an empty document.

It records extraction rather than assuming it: `meta.source` carries the
extractor, its version, and a sha256 of every extracted document. Gold offsets
are valid only against the exact text that produced them, so re-extracting with
a different library invalidates every judgment the client signed off — the hash
makes that loud instead of silent.

`.txt` and `.md` are read as **bytes** and decoded, never through text mode:
newline translation would move every offset in the file.

### 4. Client report — `src/report.py`

`write_report` in `evaluate.py` stays the developer report. The new one is the
deliverable: baseline → top failure patterns with real examples → fix backlog →
scope statement.

One rule governs it: **no number appears in it that was not produced by a run
in this repo.** The backlog derives lever attribution by diffing `Config`
objects, so a delta can never be assigned to a lever that was not moved, and a
config changing two things at once is excluded from both. Where nothing
isolated a lever, it says *not measured*.

### 5. Hybrid retrieval — `src/sparse.py`

The backlog named hybrid retrieval as a lever and no result in the repo backed
it. Now BM25 runs over the same chunks and fuses with dense using Reciprocal
Rank Fusion at k=60.

RRF rather than a weighted score sum, because cosine and BM25 scores are on
unrelated scales; normalising them introduces a weight with no principled
value — one more knob to fit to this corpus and mislead on the next one. RRF
reads only rank positions, so there is nothing to tune.

Three new configurations, and `per_query.json` records which retriever surfaced
each relevant chunk. The claim being backed is "here are the queries dense
retrieval alone gets wrong", and an aggregate delta cannot name a query.

### 6. Metadata filtering as a measured lever — `src/index.py`

The payload now carries whatever a document declares — effective date, entity,
document type, version — and `search(..., where=...)` filters on it, on both
the dense and the sparse side. `doc_filter` and `metadata_filter` became
`Config` fields, so a filter is something a run can switch off and measure.

**Nothing was fabricated for CUAD.** Its documents declare no metadata, so the
payload is unchanged. Inventing effective dates so the lever had something to
filter on would have produced a better-looking table and no evidence. What CUAD
*can* measure honestly is what dropping the `doc_id` filter costs, and the
`clause, unfiltered` configuration reports exactly that.

## What the run found

Full table in the [top-level README](../README.md#results).

- **`clause + hybrid` wins on every metric** — grounding 0.660 → 0.700,
  coverage 0.735 → 0.823. The mechanism is reordering, not candidate
  generation: fusion promoted 11 relevant chunks into the top 5 across 9
  queries that dense ranked below 5.
- **Grounding earns its place** — on `clause`, pooled coverage reads 0.735
  against complete grounding at 0.660.
- **The reranker loses on grounding** (0.660 → 0.560) despite lifting
  recall@10, and gives back most of hybrid's gain when stacked. Reported as
  measured.
- **Document scoping is worth more than every other lever combined** — 26 of
  50 queries are grounded only because the filter is there.
- **Two of five failure labels fired zero times**, for a structural reason
  that is [documented rather than hidden](metrics.md#two-labels-that-never-fire-here).

## Compatibility

Every v1 entry point still works. New parameters are keyword arguments whose
defaults reproduce the old behaviour exactly, and a test asserts the dense path
issues the identical single search it always did.

| API | change |
|---|---|
| `retrieve(...)` | `+ sparse=None`, `+ retriever="dense"`, `+ where=None` |
| `retrieve_ranked(...)` | **new** — same arguments, returns `Ranking(chunks, sources)` |
| `ChunkIndex(...)` | `+ doc_metadata=None` |
| `ChunkIndex.search(...)` | `+ where=None` |
| `Config(...)` | `+ retriever`, `+ doc_filter`, `+ metadata_filter` |
| `Result(...)` | `+ index` — the taxonomy needs the chunk list a config was scored against |
| `run_config(...)` | `+ sparse=None` |
| `run_eval.py` | `+ --baseline <config>` |

New in `per_query.json`: `span_recall@5`, `complete_grounding@5`,
`ranked_chunk_ids`, `missed_spans`, `relevant_chunk_sources`.

New output files: `results/client_report.md`, `results/taxonomy.json`.

The eval set schema gained two **optional** fields — arbitrary metadata keys on
a document, and `filters` on a query. Existing eval sets load unchanged.

## Deliberately not in v2

- **No agent or tool-call evaluation.** When it comes it is a sixth failure
  label, not a new project.
- **No LLM-as-judge anywhere in the scoring path.** Determinism is the product.
- **No dashboard, web UI, or service.** The deliverable is a repo the client
  can run and a markdown readout.
- **No refactor of `chunking.py`.** The clause regex was tuned empirically
  against these 20 contracts and the comments explain why each piece is shaped
  as it is.
- **No new repository.** All of it lives here.

## Known limits

- `ceiling-bound` and `partial-grounding` cannot fire on a contiguously-tiling
  chunker, so on this corpus the taxonomy is effectively three labels.
- The metadata lever is only measurable on CUAD via the `doc_id` filter,
  because CUAD has no version or entity conflicts. The mechanism is general;
  the demonstration is not.
- 20 contracts and 50 queries. No confidence intervals; differences of a few
  points in the aggregate table are not statistically meaningful.
- The `clause, unfiltered` collapse is partly an artifact of CUAD's templated
  questions, which is stated wherever the number appears.
